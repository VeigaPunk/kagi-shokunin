# C1 host-tripwire metric critique

**Verdict:** `HOST_TRIPWIRE total=0` is not, by itself, evidence that the intended rows were safely skipped. The tool measures matches in calls to six stubbed scripts, not host-file reads or row identities; it does not fail when a run fails, stops early, or returns `POLICY`. The planned after-criterion at `plans/round-24.md:26-32` is therefore too weak as written.

Static review only. I did not run `host-tripwire.sh`, `claim-ledger.sh verify/cells`, or any host mode; no exit code was observed. Evidence below is from the checked-out files and line ranges.

## Concrete under-counts / false zero

1. **Direct host reads bypass both the logger and current host detector.** `host-tripwire.sh:31-45` replaces six named scripts and counts only their exact basename/argument strings. `claim-ledger.sh:173-220` detects only a `bash` invocation of its declared script-name regex; `policy_check` allows `grep`, `wc`, and `test` (`:234-279`) and checks path spelling, not the resolved target. A policy-clean row such as `grep -c x corpus/home-link` (or `test -e corpus/home-link`, `wc -c corpus/home-link`) is neither a bash host invocation nor a stub call. If `corpus/home-link` is a tracked symlink to a host file, it reads that file and contributes zero. This is a concrete filesystem counterexample; the current ledger search did not establish such a row/symlink in the frozen population. The simple explicit forms (`grep ... /home/...`, `~...`, `../...`) are refused by `:267-276`, but that is lexical, not symlink containment.

2. **An unlisted bash reader runs through the scratch clone.** `bash corpus/new-reader.sh` is allowed by the first-token policy (`claim-ledger.sh:234-251`); unless its name is added to `HOST_SCRIPT_RE` (`:173`), an untagged row is not refused by `host_invocation` (`:214-220`), and the six-stub list does not replace it (`host-tripwire.sh:31-34`). Its body can open an absolute host path or delegate to `grep`; `HOME=$base/home` does not sandbox absolute paths. The tripwire can therefore both under-count it and fail its stated no-host-read safety premise.

3. **Python is an uninstrumented allowed execution class.** `claim-ledger.sh:234-235,248-250` permits the named Python gates, while `host_invocation` only parses `bash` commands (`:195-220`); `host-tripwire.sh:31-45` installs no Python wrapper. A currently allowed gate that later adds `Path.home()`/a host-file open would run without a tripwire entry. At this snapshot I found no such current HOME read in the allowed gates inspected: `feature-claims.py:214-225,250-290` resolves/opens beneath its repo root; `closure-dispositions.py:147-160` reads root-relative files; `revision-audit.py:39-64` runs Git with global/system config disabled. This is a coverage gap, not evidence that those current gates access the host. The Python rows are not themselves in the frozen 12-ID population, but `cells` can select ledger rows beyond that population.

4. **A valid zero can mean “never reached execution.”** The matcher only counts logs (`host-tripwire.sh:38-45`); the runner saves `rc` and the last output line for display but never validates either (`:48-57`), and always emits the final total (`:60-62`). In `claim-ledger.sh:504-524`, `POLICY` is checked before `HOST-SKIP`, and policy, host skip, and substrate defer all `continue` before `C_RUN`/command execution. A malformed stamp can also make `verify_stamps` die before `verify_claims` (`:1081-1084`; `load_stamps` dies at `:407-417`). Thus zero can accompany `POLICY`, `FAIL`, setup exit 2, timeout, or an early exit—not successful default host skipping. In particular, post-change `HOST-SKIP` should be shown per expected ID; a zero logger count alone does not distinguish that from a command refused before the host gate.

5. **The after revision is not bound to the candidate unless the caller does it.** The tool clones exactly `REV` (`host-tripwire.sh:28-29`) and overlays only explicitly listed `SRC FILE...` arguments (`:23-30`). The plan's invocation omits those overlay arguments (`plans/round-24.md:28-31`). If the candidate is uncommitted or `REV` is stale/BASE, that command tests the old tree. The output truncates `REV` to 12 hex digits (`host-tripwire.sh:61-62`) and does not report any overlay manifest/digest, weakening provenance of a purported post-change zero (freshness/calibration).

## Over-count and depth behavior

`count()` has no row ID or parent-invocation identity: each matching stub line counts (`host-tripwire.sh:33,38-45`). A non-population wrapper row that calls `bash corpus/drift-pins.sh` produces the same `drift-pins.sh ` record as R11-04/R18-01 and is attributed to a population execution. The current obvious wrapper, R15-01's `checklist-run.sh`, is itself stubbed, so that particular delegation is suppressed in this harness; the attribution flaw remains for any un-stubbed wrapper. The same `drift-pins.sh` signature also cannot distinguish R11-04 from R18-01. Moreover `total` sums four separate runs, and cells may rerun a row: it is invocation-count, not unique-row-count.

Depth greater than two is **not** directly dropped: the stub records `CLAIM_LEDGER_DEPTH` and `count()` matches regardless of it (`:33,41-44`). But the depth is never asserted or used, and each repeated call can inflate the count. `cells_evidence` skips only a row whose command directly invokes `claim-ledger.sh` (`claim-ledger.sh:918-930`); a wrapper around that command is not caught. A nested run may therefore recurse/timeout; since the tripwire still reports partial counts and does not reject nonzero `rc` (`host-tripwire.sh:48-57`), depth>2 can yield a misleading partial or zero result.

## Smallest safe correction

- Make the post measurement fail closed: bind it to the exact candidate full revision (or pass and report a digest-checked `SRC FILE...` overlay); require each `verify`/`cells` run to reach its expected terminal summary and exit; parse per-row statuses. For `verify`, require every frozen host ID to be `HOST-SKIP` (the expected population is 12 per plan `:26-31`), with no `POLICY`, `FAIL`, or `DEFER` for those IDs. For `cells`, derive its selected IDs from the scorecard and require each selected population ID's expected disposition, accounting for the intentional `SKIP-SELF` case (R13-03). Keep `host_skipped`/`rows_run` summary values as cross-checks, not substitutes for IDs.
- Stop calling the current signature counter a general host-read counter. For this frozen 12-row claim, emit a structured test event at the ledger's row decision/dispatch point (`row_id`, depth, status = execute/host-skip/policy/defer) and count IDs, not child-script basename matches. If the claim is intended to cover arbitrary host reads, add a scratch-only filesystem sandbox/deny-and-trace boundary (or resolved-path enforcement for every allowed command); six script stubs plus `HOME` replacement cannot establish that broader property.
- Treat `cells` recursion beyond the expected bound as an instrument error, not extra “rows”; assert a maximum depth and report per-run counts, rather than summing unmatched/partial logs into a success-shaped `HOST_TRIPWIRE` line.

**Axes impacted:** operability (instrument fails to distinguish safe skip from non-execution), calibration (zero is not a row-bound outcome; counts have invocation/attribution ambiguity), freshness (revision/overlay provenance is not bound in the output).
