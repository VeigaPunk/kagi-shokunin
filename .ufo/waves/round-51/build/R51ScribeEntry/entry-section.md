## Measured (round 51 — OpenBao 2.7.2 dev server, 127.0.0.1, response wrapping)

source: S108 (https://openbao.org/docs/concepts/response-wrapping/, §Overview, §Response-Wrapping token operations, §Response-Wrapping token validation, Version 2.7.x, opened 2026-11-07; capture `.ufo/waves/round-51/capture/S108.body`, decoded body sha256 `a555301e…f9cc32ed55`, 37186 B)

`bash corpus/openbao-wrap-trial.sh --work <scratch dir>` drives the `bao` CLI against a throwaway `bao server -dev` (in-memory storage, a random root token kept only in the scratch tree and deleted with it, started under `setpriv --pdeathsig KILL`); every caller `BAO_*`/`VAULT_*` variable is unset and `HOME` points into that tree. Wrapped values are random nonces written to the dev server's default KV v2 `secret/` mount, and neither a token value nor a nonce is printed. Each test prints one line `TRIAL T<n> HOLDS|BROKEN|ERROR <detail>`; the run ends `OPENBAO_WRAP_TRIAL: HOLDS|BROKEN|ERROR holds=<n> broken=<n> error=<n> bao=<version>` and exits 0 (all HOLDS), 1 (any BROKEN) or 2 (setup failure or any ERROR). A test HOLDS only when its designated client-side falsifier flips it to BROKEN (`plans/round-51-c1.sh`, SH1–SH5).

- T1 single use (OpenBao 2.7.2): the first `bao unwrap` of a wrapped `kv get` returns the value; a second unwrap of the same token is refused with the server's `wrapping token is not valid or does not exist` — measures S108 §Overview, “only a single party can ever unwrap the token and see what's inside” (located, count=1).
- T2 wrap TTL (OpenBao 2.7.2): a `-wrap-ttl=2s` token can no longer be unwrapped after 4 s while the KV secret itself stays readable — measures S108 §Overview, “the response-wrapping token has a lifetime that is separate from the wrapped secret” (count=1).
- T3 lookup (OpenBao 2.7.2): `sys/wrapping/lookup` with no client token reports `creation_path` `secret/data/t3` and does not consume the token; after the unwrap the same lookup is refused — measures S108 §Response-Wrapping token operations, “This path is unauthenticated and available to response-wrapping tokens themselves” (count=1), and §Response-Wrapping token validation, “This immediately tells you if the token has already been unwrapped or is expired” (count=1).
- T4 rewrap (OpenBao 2.7.2): `sys/wrapping/rewrap` returns a different token that unwraps to the same value; the old token is refused — measures S108 §Response-Wrapping token operations, “Allows migrating the wrapped data to a new response-wrapping token” (count=1).
- T5 creation path (OpenBao 2.7.2): a value read out and wrapped again through `sys/wrapping/wrap` carries creation path `sys/wrapping/wrap`, not `secret/data/t5`, so a client that checks the exact expected path detects the re-wrap while a client that checks only the prefix `secret/` does not — measures S108 §Response-Wrapping token validation, “it is possible that the data contained inside was read and then put into a new response-wrapping token” (count=1) and “exact matches on the path are best there” (count=1).

Re-run: `bash corpus/openbao-wrap-trial.sh --work <dir>` (starts and kills its own throwaway dev server; needs `bao`, `python3` and `setpriv` on `PATH`).

**Does not establish:**

- No server-side guarantee: the falsifier shims the counter uses are client-side `bao` dispatchers, so a discriminating test excludes a lying CLI under these conditions, not a misbehaving, compromised or non-conforming server.
- One version: OpenBao 2.7.2 only (the pinned `~/.local/bin/bao`, sha256 `9c5f3628…b788`); no other release, no Vault binary and no Vault/OpenBao parity.
- KV v2 only: the dev server's default `secret/` mount through `kv put`/`kv get`; no other engine wraps a response here (the page's `pki` example is not exercised), and no `X-Vault-Wrap-TTL` header, no Go API `SetWrappingLookupFunc`, and no `cubbyhole` enumeration path is driven — the CLI `-wrap-ttl` flag is the only wrapping trigger.
- No audit-log or policy-TTL bounds: the page's validation step points at “likely with the assistance of OpenBao's audit logs to see if the token really was unwrapped” (count=1) and its creation section says “policies can control minimum/maximum wrapping TTLs” (count=1); the trial enables no audit device and sets no policy TTL bound, so neither is measured, and the wrap TTLs used (2–60 s) are neither the product default nor a maximum.
- Dev mode: in-memory storage, HTTP on 127.0.0.1, no TLS, no seal/unseal, no HA, and no policy model beyond `default`; none of it is evidence about a deployed or production configuration.
