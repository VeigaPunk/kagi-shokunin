## What an audit device is (S115 §Audit devices; S116 §audit, §Examples)

An audit device is a sink that receives the log of every API request and its response. S115 defines the class as “the components in OpenBao that collectively keep a detailed log of all requests to OpenBao, and their responses.” Because every operation with OpenBao is an API request/response, “when using a single audit device, the audit log contains every interaction with the OpenBao API, including errors” — minus the paths in the next section. The operator surface is `bao audit enable`, `bao audit disable` and `bao audit list` (S116: “The audit command groups subcommands for interacting with OpenBao's audit devices. Users can list, enable, and disable audit devices.”). S116's worked examples are the custody-relevant ones: enabling the file device at a path prints `Success! Enabled the file audit device at: file/`, `bao audit list` shows a `file/` row of type `file`, and disabling prints `Success! Disabled audit device (if it was enabled) at: file/`.

Quote/locate: S115 §Audit devices, “Audit devices are the components in OpenBao that collectively keep a detailed log of all requests to OpenBao, and their responses.” → `count=1`; S116 §Examples, “Success! Enabled the file audit device at: file/” → `count=1`.

## The value form: HMAC-SHA256 with a salt, and what is not hashed (S115 §Format, §Sensitive information)

Each audit line is a JSON object whose `type` field is `request` or `response` — S115 says only those two types exist — and a line contains “all of the information for any given request and response”; the log as a whole contains the full request and response objects for every interaction. Request and response records are matched “utilizing a unique identifier assigned to each request.” Most strings in requests and responses are “hashed with a salt using HMAC-SHA256”; the purpose is that “secrets aren't in plaintext within your audit logs”, while an operator who has the device's hash function and salt can reproduce the HMAC through the `/sys/audit-hash` API endpoint and compare it with a logged value. Two limits are documented on the same page: only strings “that come from JSON or returned in JSON are HMAC'd”, so integers, booleans and other data types pass through in plaintext (the page recommends supplying sensitive data as JSON strings, in quotes), and the scheme has deliberate exceptions (“such as auth and secrets”) that operators can extend with `secrets enable` and then tune. The literal wire form `hmac-sha256:` is not on either page — the string `hmac-sha256` occurs zero times in both decoded bodies — so the prefix spelling is a measured fact (T2), not a documented one.

Quote/locate: S115 §Sensitive information, “Most strings contained within requests and responses are hashed with a salt using HMAC-SHA256.” → `count=1`; “Currently, only strings that come from JSON or returned in JSON are HMAC'd.” → `count=1`; “this can be done with the audit device's hash function and salt by using the /sys/audit-hash API endpoint” → `count=1`.

## `log_raw` and `hmac_accessor` (S115 §Common configuration options)

`log_raw` defaults to `false`; when enabled it “logs the security sensitive information without hashing, in the raw format.” `hmac_accessor` defaults to `true`; when enabled it “enables the hashing of token accessor.” Read together with the value-form section, a default device hashes request/response strings and hashes token accessors, and `log_raw=true` is the deliberate switch that writes the values a default device would HMAC. Consequence (inference from those two rows, not a sentence on the page): the file written by a `log_raw` device is itself secret material and has to be protected as such, and any HMAC comparison against it is meaningless for the raw fields. Two neighbouring options matter for the same custody: `prefix` writes a customizable string before each line and, starting with OpenBao v2.3.2, requires `allow_audit_log_prefixing = true` in the server configuration; `skip_test` (when set to `"true"`) suppresses the enable-time test probe that otherwise fails the enable if the destination is unreachable, which S115 notes “can block unsealing.” Two more bound what a log can prove: `format` accepts only `"json"`, and `elide_list_responses` rewrites `response.data.keys` and `response.data.key_info` in `type=response, request.operation=list` records to a simple integer — the number of entries, not their names — so an elided log can say how many items a list returned but cannot reconstruct which.

Quote/locate: S115 §Common configuration options, “log_raw (bool: false) - If enabled, logs the security sensitive information without hashing, in the raw format.” → `count=1`; “hmac_accessor (bool: true) - If enabled, enables the hashing of token accessor.” → `count=1`; “we will enable a new model where audit devices are managed within the server configuration itself” → `count=1`; “The only valid value is "json"” → `count=1`; “The values of response.data.keys and response.data.key_info will be replaced with a simple integer” → `count=1`.

## The documented non-audited paths (S115 §Audit devices)

The “every interaction” claim carries a named exemption list. S115 states the audit log covers every interaction “except for a few paths which do not go via the audit system”, then lists eight unconditional paths: `sys/init`, `sys/seal-status`, `sys/seal`, `sys/unseal`, `sys/leader`, `sys/health`, `sys/storage/raft/bootstrap` and `sys/storage/raft/join`. Three further paths — `sys/metrics`, `sys/pprof/*` and `sys/in-flight-req` — are non-audited “if the relevant listener configuration settings allow unauthenticated access”. A custody claim therefore has to exclude those windows, and a probe that uses one of them (T5 uses `bao status`) cannot use audit presence as its evidence of anything. The identification of the `bao status` CLI call with the `sys/seal-status` path is not made on S115 or S116 (see G1); what S115 establishes is that the path itself is not audited.

Quote/locate: S115 §Audit devices, “except for a few paths which do not go via the audit system” → `count=1`; “sys/init sys/seal-status sys/seal sys/unseal sys/leader sys/health sys/storage/raft/bootstrap sys/storage/raft/join” → `count=1`.

## Disable and re-enable: a new salt (S115 §Enabling/Disabling audit devices; S116 §Examples)

Disabling a device stops delivery immediately — “When an audit device is disabled, it will stop receiving logs immediately. The existing logs that it did store are untouched.” — and it breaks HMAC comparison against entries recorded under the old salt. Both pages carry the same warning: once a device is disabled, “you will no longer be able to HMAC values for comparison with entries in the audit logs. This is true even if you re-enable the audit device at the same path, as a new salt will be created for hashing.” Consequence (inference): HMAC values captured before a disable cannot be matched after a re-enable, so cross-time correlation requires keeping the device enabled and preserving its salt-bearing state; S115 documents no salt export, so a disable/re-enable is a custody break for comparison purposes. T4 measures the salt change on one value before and after a re-enable.

Quote/locate: S115 §Enabling/Disabling audit devices, “When an audit device is disabled, it will stop receiving logs immediately. The existing logs that it did store are untouched.” → `count=1`; “as a new salt will be created for hashing” → `count=1`; S116 §Examples, “Once an audit device is disabled, you will no longer be able to HMAC values for comparison with entries in the audit logs. This is true even if you re-enable the audit device at the same path, as a new salt will be created for hashing.” → `count=1`.

## Enabling is a cluster-wide act (S115 §Enabling/Disabling audit devices)

When a server is first initialized, “no auditing is enabled”; devices are enabled by a root user through `bao audit enable` or the `audit` stanza. Enabling through the API (and therefore the CLI) can create files at arbitrary host locations or send network requests, so starting with OpenBao v2.3.2 the server configuration must set `unsafe_allow_api_audit_creation = true`. The same paragraph is stale against its own page: rendered at “Version 2.7.x” on 2026-11-07, it still says “In future releases (v2.4+), we will enable a new model where audit devices are managed within the server configuration itself” — a prospective sentence whose named version is already older than the page's label, and the page does not say whether that model shipped. Read it as a page-level inconsistency, not as a description of 2.7.2. Device configuration is replicated to all nodes in a cluster by default, and the page warns to ensure every node can log to the device before enabling it, “to avoid OpenBao being blocked from serving requests.”

Quote/locate: S115 §Enabling/Disabling audit devices, “the unsafe_allow_api_audit_creation = true option must be set in the server configuration starting with OpenBao v2.3.2” → `count=1`; “In future releases (v2.4+), we will enable a new model where audit devices are managed within the server configuration itself” → `count=1`; “Audit device configuration is replicated to all nodes within a cluster by default.” → `count=1`; “to avoid OpenBao being blocked from serving requests” → `count=1`.

## Multiple devices and the failure rule (S115 §Enabling multiple devices, §Blocked audit devices)

With several devices enabled, “OpenBao will attempt to send the audit logs to all of them”, which yields redundant copies and a way to check the logs for tampering; the complete record is the “aggregate/union of the logs from each audit device.” Success is defined per request, not per device: “OpenBao considers a request to be successful if it can log to at least one configured audit device”. The failure rule distinguishes two classes. A blocking failure is a write attempt that “never completes” — unlikely for a local disk, possible for a network device. Non-blocking failure of one device still lets requests complete provided at least one device writes; a blocking failure makes requests “hang until the blocking is resolved.” With no device able to record, the server “will not respond to requests”. The page's recommendation to run more than one device follows from that: audit failure can stop service, and the alternative to being down is sometimes a silently partial log, which is why the union is the evidence.

Quote/locate: S115 §Enabling multiple devices, “OpenBao considers a request to be successful if it can log to at least one configured audit device” → `count=1`; §Blocked audit devices, “If any of the audit devices fail in a blocking fashion however, OpenBao requests will hang until the blocking is resolved.” → `count=1`; “OpenBao will not respond to requests when no enabled audit devices can record them.” → `count=1`.

## What it does not establish

- One binary, one host. The measured section is OpenBao 2.7.2 on one machine; a second minor line or a distribution build can differ, and S115's own label is the `2.7.x` line, not a patch.
- A dev server, not a deployment. The trial uses `bao server -dev` with in-memory storage on 127.0.0.1 and a one-line `-config` opt-in. It does not exercise a storage backend, replication, a cluster of nodes, restart, seal/unseal lifecycles, or the documented cluster-wide replication of audit device configuration. The default dev configuration without the opt-in failed at the enable step (T1's default-refusal leg), so nothing here describes a default dev server's audit surface.
- The declarative model is not exercised. S115 calls config-managed audit devices the future direction; the trial uses the legacy CLI path under the opt-in flag and never enables a device through the `audit` stanza or a declarative section of the server configuration.
- One audit device type. The trial enables the file device; syslog, socket, HTTP and plugin devices are not exercised.
- No real secret and no policy. Values are random nonces and the token is a throwaway dev root token; the trial counts the raw device's plaintext value and token occurrences but prints neither. No rotation, lease, access policy or operator custody procedure is measured. `log_raw` output is judged by count inside the trial and is never committed.
- The multiple-device blocking rule is quoted from S115, not measured. The trial enables two devices and measures the raw/default split, but does not wedge one device into a blocking failure.
- The `sys/seal-status` membership of the non-audited list is documented (S115) and T5 observes that `bao status` leaves no audit entry; the CLI-to-path identity itself is not stated on S115/S116 (G1).
- No salt persistence or export is tested beyond the single disable/re-enable in T4; nothing here says a salt survives or does not survive a restart, a device move, or a cluster join.
