     today, and 35 of their 36 declared quotes locate in the named body (S115
     does not)". My independent re-derivation: 36 path rows, 36 bound, 35
     located, S115 the sole non-locating row. EVERY CLAUSE AGREES.

     prose=120, path_rows=36. The target `located=36` is therefore NOT
     reachable at BASE: it requires the S115 quote re-cut that the plan itself

     corpus/source-fetches.tsv to a locating quote", owned by L1). The plan
     states this correctly in its evidence paragraph — the two statements are
     consistent (evidence = today; predicate = after the round's landing
     surface). NOT a disagreement; recorded so the executor does not read
     "located=36" as a BASE reading.

A-3. The plan says the C1 predicate's `located` counts "those rows whose
     declared quote (col 13) locates count >= 1 in that file under the declared
     normalization (col 14)". My census confirms 31 of the 36 path rows declare
     rendered-text-v1 and 5 declare raw-literal-v1; all 5 raw-literal rows

A-4. NO numeric disagreement was found with the plan's C2 table. All seven

DEFECT F-2 (calibration — the plan's own target number contradicts its own
            stated population, and the repair sits outside C1's landing surface)
  The C1 predicate freezes `located=36` and guard (a) freezes the exact clean
  line `SOURCES_CAPTURES: CLEAN (path_rows=36 bound=36 located=36 prose=120)`.
  Measured at BASE: located=35, because S115's declared quote does not locate
  in its own named body. The plan's landing surface DOES list the S115 re-cut,
  but that row is owned by L1 (`corpus/source-fetches.tsv` — L1 only), while
  `plans/round-67-c1.sh` is owned by R67ExecCounterC1 and
  `corpus/sources-census.sh` by R67ExecGate. So the C1 counter and the gate
  cannot both read located=36 until L1 lands the re-cut: two of the three
  seats cannot deliver their half of the predicate independently. A counter

    SOURCES_CAPTURES: FAILED (defects=1 path_rows=36 bound=36 located=35 prose=120)
  — the correct honest reading, and a guard=(0) under a naive implementation.
  The plan's kill rule ("the target is missed if … located < 36") therefore
  penalises an executor whose bytes are correct. This is the round-66 M66-8
  shape (a leg that measures state another seat owns) recurring in the
  predicate's arithmetic.
  Severity: HIGH — it is a coordination hazard, not a wording nit.

DEFECT F-3 (vacuity — the plan's `catch=6/6` mutation battery has one leg the
            frozen predicate cannot catch as written)
  The frozen path-shape predicate (seat interface + plan §C1) is:
    col16 contains '/' AND matches ^[A-Za-z0-9._][A-Za-z0-9._/-]*$
  Measured: an ABSOLUTE location such as `/etc/passwd` does NOT match that
  regex (the first character class excludes '/'), so under the predicate as
  frozen an absolute location is classified PROSE and is never checked — yet
  the plan's mutation battery lists "absolute location" among the six legs and
  the frozen reason vocabulary includes `capture-outside-root`, which is
  otherwise reachable only by a ".." escape.
  I verified this empirically on a BASE extraction: with the predicate applied
  strictly, the absolute-location leg produced
    SOURCES_CAPTURES: FAILED (defects=1 path_rows=35 bound=35 located=34 prose=121)
  — the absolute row was counted as PROSE (path_rows 36->35, prose 120->121),
  and NO SC_CAPTURE finding named the absolute row. The absolute-location leg
  is therefore uncatchable under the strict frozen predicate, and the strict
  run also breaks guard (a)'s exact clean line (path_rows/prose would shift).
  The in-flight executor has already solved this by WIDENING the shape test
  to also accept an absolute path:
      [[ $loc =~ ^/[A-Za-z0-9._][A-Za-z0-9._/-]*$ ]]
  (corpus/sources-census.sh, cap_is_shaped, in the live working tree). With
  that widening the absolute leg IS caught:
      FINDING SC_CAPTURE id=S164 capture-outside-root
      SOURCES_CAPTURES: FAILED (defects=2 path_rows=36 bound=35 located=34 prose=120)
  and the clean tree still prints path_rows=36 prose=120, so guard (a) holds.
  The widening is CORRECT and necessary, but it is a change to a FROZEN
  PREDICTIVE TERM and must be recorded as such (the plan says the predicate is
  the plan's, the counter's code and the receipt's label). If the executor
  ships the strict predicate, caught=5/6 and the target is missed for a reason
  that has nothing to do with the candidate's quality.
  Severity: HIGH — this is the one place where the frozen text and the frozen
  target are mutually unsatisfiable.
